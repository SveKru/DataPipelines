# Extract column lineage

This framework already tracks row-level lineage automatically (the `map_` column +
`record_tracing`, see ARCHITECTURE.md's "Lineage / record tracing" section), but it
is not column-aware — a join or groupby merges lineage per row, not per column. This
skill produces column-level lineage by statically reading the table's processing
code, since that's the only place the true source-column mapping exists.

## Steps

1. **Find the table's processing branch.** From the table's `_<layer>` suffix,
   locate `processing/processing_<layer>.py` and find the
   `elif table_name == "<table>":` branch that builds it.
2. **Find the table's schema entry.** Locate it in `schema/schema_<layer>.py` to get
   the full, ordered output column list.
3. **Read the branch line by line** and, for every output column, trace which
   upstream table(s) and column(s) it comes from:
   - A column selected/renamed straight from a source `CustomDF` → that source
     table + column.
   - A column computed from an expression (e.g. `pl.when(...)`, arithmetic, string
     ops, casts) → every column referenced inside that expression, from whichever
     source table was in scope at that point in the branch.
   - A column produced by a `custom_groupby` aggregation → the column(s) the
     aggregation expression reads, from the table that was being grouped (which may
     itself already be a join of multiple sources — trace back through the join if
     so).
   - A column present in more than one joined source (e.g. a shared join key) →
     list every source table that supplies it, not just one.
4. **Exclude internal/engine-managed columns.** Do **not** include `RecordID`,
   `from_date`, or `to_date` in the lineage output — these are generated by
   `write_table()`/`add_record_id()`/`apply_scd_type_2`, not derived from any
   business source column, and including them just adds noise to the lineage graph.
5. **Write the result as a JSON file** (not a skill, not a script — a plain data
   file), named `<table_name>_column_lineage.json`, shaped like:

```json
{
  "table": "<table_name>",
  "generated_from": "processing/processing_<layer>.py::generate_table_<layer> (\"<table_name>\" branch)",
  "columns": {
    "<output_column>": {
      "sources": [
        { "table": "<source_table>", "column": "<source_column>" }
      ],
      "derivation": "<short plain-English note on how it's computed>"
    }
  }
}
```

   - `sources` is a list because a column can have more than one upstream
     table/column (joins, groupby aggregations combining several columns, shared
     join keys from multiple tables).
   - If a column is entirely engine-generated with no business-logic source (this
     should only ever apply to `RecordID`/`from_date`/`to_date`, which are already
     excluded per step 4), don't create an entry for it at all — skip it rather
     than writing an empty `sources: []`.
   - Keep `derivation` short — one sentence, plain English, no need to restate the
     column name.

## Notes

- This is read-only analysis. Don't run the pipeline or inspect actual data — the
  lineage comes entirely from reading the processing branch's source code.
- If the branch reads from another `_enriched`/`_datamodel` table that is itself
  derived (not raw), you can stop at that table/column — you don't need to recurse
  further upstream unless explicitly asked for full multi-hop lineage.
